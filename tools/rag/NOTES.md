# RFS 챗봇 (RAG) 작업 노트

학회 자료를 근거로 질문에 답하고, 보고서·모델링을 옆에서 코칭하는 챗봇.
이 파일은 단계마다 무엇을 왜 했고 결과가 어땠는지 숫자로 남긴다. 원문 자료는 비공개 저장소(`rfs-cafe-data`)에만 있고, 여기에는 코드와 통계만 둔다.

## 0. 목표
- 학회 자료(리포트, 세미나, 엑셀 모델, 가이드)만 근거로 답한다. 없으면 없다고 한다.
- 답마다 출처(문서, 페이지)를 단다.
- 단순 검색 봇이 아니라 코칭: 회사 상황을 먼저 묻고, 학회 사례를 보여주고, 방법을 같이 고른다.
- 자료마다 신뢰도가 다르다. 정규 리포트(A)를 모범 사례로, 신입 투자제안서(C)는 아이디어 사례로만 쓴다.

## 1. 수집 (tools/cafe/download.mjs)
- 네이버 카페 25개 게시판, 글 1,007개, 3.6GB.
- 방식: Playwright로 실제 크롬을 띄우고 사람이 로그인 → 그 세션 쿠키로 카페 웹이 내부에서 쓰는 JSON API를 호출.
  - HTML 파싱 대신 API: 카페 화면은 iframe 구조라 자주 바뀌고, JSON이 더 안정적이다.
  - 요청 사이 0.8~1.6초 대기, 한 번에 한 글씩. 받은 글은 `meta.json`으로 표시해서 이어받기.
  - 작성자 이름은 저장하지 않는다. 로그인 프로필 폴더는 업로드에서 제외.
- 부딪힌 문제
  - 로그인 쿠키가 브라우저 종료 시 사라짐 → 시작할 때 `NID_AUT` 쿠키 확인.
  - 제목이 "입니다."처럼 점으로 끝나면 윈도우가 폴더를 못 연다 → 이름 끝 점·공백 제거 (`fixnames.mjs`).
  - 3GB 한 번에 push 시 GitHub HTTP 500 → 게시판 단위로 나눠 커밋·push.

## 2. 파싱 (tools/rag/parse.py)
형식별 추출
| 형식 | 방법 |
|---|---|
| PDF | PyMuPDF 페이지별 텍스트. 절반 넘는 페이지에 반복되는 줄(머리말·꼬리말)과 14자 이하 숫자줄(차트 축) 제거 |
| docx / pptx | zip 안의 XML에서 문단(`w:p`, `a:p`) 단위로 직접 추출. pptx는 슬라이드별 페이지 유지 |
| hwp | HWP 5.0 OLE 구조를 직접 읽어 `BodyText/Section*`의 PARA_TEXT(태그 67) 레코드만 디코딩 |
| xlsx | 아래 "엑셀 모델" 참고 |
| xls | xlrd로 값만 (구 형식이라 수식 없음) |
| zip | 풀어서 안의 파일을 같은 방식으로. 윈도우 압축 파일명은 cp949로 복원 |

엑셀 모델 (밸류에이션 논리를 살리는 게 핵심)
- Valuation, WACC, 가정, 추정 시트: 수식 안의 셀 주소를 그 행의 항목 이름으로 바꿔 문장처럼 만든다.
  예) `=C6*C7` → `⟨식: [24F EPS]*[Target P/E]⟩`
- 같은 행에서 열만 바뀌는 수식(연도별 반복)은 한 번만 풀어 쓴다.
- IS/BS/CF 같은 재무제표 시트는 숫자 수천 개라 검색만 방해 → 항목명과 열 머리만 남긴다.
- 밸류에이션 시트를 앞에 두고 모델당 4만 자에서 자른다.
- 결과: 모델 텍스트 1,313만 자 → 739만 자 (-44%).

중복 제거 (2단계)
1. MinHash LSH (5-gram, 임계값 0.8): 사이트 리포트와 카페에 같은 리포트가 올라간 경우 등. 118그룹.
2. 같은 글 안 포함도: 같은 리포트를 PDF와 워드로 같이 올린 경우, 서식 차이로 Jaccard가 0.3~0.7에 머물러 1단계에서 안 잡힌다.
   작은 쪽 문서의 8-gram이 큰 쪽에 50% 이상 들어있으면 중복으로 본다. 48건 추가 제거.
- 남길 문서 우선순위: 사이트 리포트 > PDF > PPT > 글자 수.

문서 종류·등급 (규칙 기반, 애매한 건 이후 LLM 재분류 예정)
| 종류 | 등급 | 쓰임 |
|---|---|---|
| company (기업 리포트) | A | 리포트 구성, 투자포인트, 밸류에이션 사례 |
| industry (산업 리포트) | A | 산업 지식 |
| guide (가이드·양식·교육) | A | 방법론 질문 |
| model (엑셀) | A (검산 예정) | 추정·밸류에이션 방법 |
| study, macro, fund_report, post | B | 보충 |
| proposal (투자제안서, 신입) | C | 아이디어 사례만 |

### 결과 (2026-10-12)
| 항목 | 값 |
|---|---|
| 문서 (중복 제거 전 → 후) | 2,346 → 2,180 |
| 제거한 중복 | 166 (사이트·카페 중복 88그룹 포함) |
| 글자 수 (중복 제거 후) | 3,431만 자 |
| PDF 페이지 | 14,871 (그중 글자 거의 없는 페이지 1,549, 10%: 이미지 슬라이드·스캔본, OCR 후보) |
| 등급 | A 1,250 / B 592 / C 338 |
| 실패 | 56 (zip 안 이미지·글꼴 50, 구형 ppt 5, 깨진 zip 1) |

남은 숙제
- 이미지 페이지 10%: 차트·표가 이미지인 슬라이드. 필요하면 OCR 또는 Claude 비전으로 설명문 생성.
- 구형 .ppt 5개: 변환 도구 필요.
- 엑셀 모델 검산(목표주가 계산, 비어 있는 가정, 비현실적 숫자)과 밸류에이션 DB 추출은 API 키 준비 후.

## 3. 청킹 (tools/rag/chunk.py)
- 리포트는 섹션 제목("Investment Point 1", "Valuation", "산업분석" 등)에서 먼저 자르고, 긴 섹션은 문단 경계에서 약 1,200자로 나눈다 (겹침 200자).
  - 고정 길이로만 자르면 "투자포인트 1의 결론 + 투자포인트 2의 도입"처럼 주제가 섞인 청크가 생긴다.
- 청크마다 페이지 범위를 남긴다 → 답변에 "OO 리포트 p.7" 출처.
- 청크 앞에 머리글을 붙인다: `대한항공 | 19-1학기 | 기업 리포트 | Valuation | p.6`.
  "매출이 30% 늘었다"는 문단만으로는 어느 회사 얘기인지 알 수 없어서 (Contextual Retrieval과 같은 생각).
- 엑셀 모델은 시트 단위.
- 부딪힌 문제
  - 매 페이지 머리말 "R.F.S. Securities Research Ⅰ 12"가 페이지 번호 때문에 반복 줄 제거에 안 걸림 → 정규식으로 제거.
  - 표지의 "목표주가" 상자를 섹션 제목으로 오인해 리포트 전체가 "목표주가" 섹션이 됨(2,024청크) → 제목 규칙에서 제외.
  - PDF는 폭에 맞춰 줄이 끊겨 "부\n문"처럼 단어가 갈림 → 문장이 안 끝난 줄은 잇고, 폭을 꽉 채운 한글 줄끼리는 띄어쓰기 없이 붙임.
- 결과: 문서 2,162개 → 청크 43,573개, 길이 중앙값 936자 (p10 280, p90 1,192).

## 4. 평가셋 v0 (비공개 저장소 eval/eval_v0.jsonl)
- 41문항: 사실 14, 방법론 7, 가이드 5, 코칭 8, 글쓰기 2, 여러 문서 종합 2, 자료에 없음·거절 3.
- 정답은 실제 청크 ID로 고정 (문구 검색으로 찾아서 존재를 확인).
- 한계: 코칭·종합 질문은 정답 문서가 여러 개일 수 있는데 지금은 1~2개만 정답으로 둠 → 검색 점수가 실제보다 낮게 나옴. 답변 단계에서 LLM 채점으로 보완 예정.

## 5. 검색 기준선: BM25 (tools/rag/eval_retrieval.py)
- 한국어 형태소 분석기 없이 2글자 묶음(bigram) + 영문·숫자 단어로 BM25.
| 지표 | 값 |
|---|---|
| 문서 hit@1 / @5 / @20 | 31.6% / 50.0% / 68.4% |
| 청크 hit@5 | 28.9% |
| 문서 MRR | 0.398 |
| 유형별 문서 hit@5 | 사실 71%, 방법론 71%, 가이드 60%, **코칭 12.5%**, 글쓰기·종합 0% |
- 해석: 질문에 회사 이름이 들어 있으면 키워드로 꽤 찾는다. "항공사 밸류에이션은 뭘로 해?"처럼 리포트와 단어가 다른 질문은 거의 못 찾는다.
  → 의미 기반 검색(임베딩)이 필요한 이유를 숫자로 보여주는 기준선. 다음 단계에서 같은 평가셋으로 비교한다.
